架构总览

fping-monitor · 代码地图

单进程长驻容器，6 个 .py + 1 个 DDL + 2 个 YAML。核心是 批量化 fping + 状态机防抖 + 可插拔通知 + 配置热加载。这一页用 多张图带你看清：模块怎么分、数据怎么流、状态怎么变、配置怎么热更、哪里可以扩展。

容器常驻 单进程 热加载 DingTalk · 完整 Cuckoo · 占位 Host Tags

01 · 模块分层

5 个职责层 + 1 个数据模型

入口 · monitor.py

解析 --config（顶层）+ --servers（run 子命令专属）， 默认子命令是 run；加载配置 + 初始化日志，进入常驻循环。

build_detector / build_notifier / run_daemon

调度 · scheduler.py

Scheduler.run_once + StateMachine._advance 纯函数状态转移。

Scheduler · StateMachine · CycleResult

检测 · detector.py

单次 fping 批检，输出 {name: bool}。Detector 协议，可替换。

FpingDetector

通知 · notifier.py

统一 notify_down/recover。默认 异步派发 （ThreadPoolExecutor，webhook 不阻塞 fping 循环）+ 防抖 （min_interval_s 控制同一 host 不刷屏）。

Notifier · DingTalk · Cuckoo 占位

持久 · database.py

sqlite3 薄封装，启动时应用 sql/schema.sql，host/event 两类操作。

Database · _encode/decode_tags

基础 · models + util

models.py 定义 Host(含 tags)/Event/枚举；util.py 提供 YAML/日志/fping 解析。

models.py · util.py

三个不变式：Detector 只输出 {name: bool}， StateMachine 不知道 fping 存在；Notifier 只接收 Host（含 tags）， StateMachine 不知道有钉钉；Channel 不知道有 ThreadPoolExecutor， 同步 / 异步切换由 Notifier 单独决定。中间两层都是扩展点。

03 · 时序：单次循环内部调用

从 db.list_hosts() 到 webhook POST

sequenceDiagram
  autonumber
  participant MON as monitor.py
  participant SCH as Scheduler
  participant DB as Database
  participant DET as FpingDetector
  participant FP as fping
  participant SM as StateMachine
  participant NT as Notifier
  participant EX as ThreadPoolExecutor
  participant DT as DingTalkChannel

  MON->>SCH: run_once()
  SCH->>DB: list_hosts()
  DB-->>SCH: [Host, ...]
  SCH->>DET: detect(hosts)
  DET->>FP: subprocess.run([fping, ...])
  FP-->>DET: stdout / stderr
  DET-->>SCH: {name: bool}
  SCH->>SM: step(alive)
  loop 每台 host
    SM->>SM: _advance(host, is_alive)
    SM->>DB: update_host_state(...)
    alt fired AND 旧状态非 UNKNOWN
      SM->>DB: insert_event(...)
      SM->>NT: notify_down/recover(host)
      alt min_interval_s > 0 AND 同 (ch, host, kind) 在窗口内
        NT-->>SM: 防抖跳过（debug 日志）
      else
        NT->>EX: submit(_safe_call, ...)
        EX-->>NT: Future（立即返回）
      end
      par 后台线程
        EX->>DT: notify_down/recover(host)
        DT->>DT: requests.post(webhook)
      end
    end
  end
  SM-->>SCH: CycleResult
  SCH-->>MON: CycleResult
  MON-->>MON: sleep(interval) 继续下一轮

  Note over MON,DB: SIGTERM 触发优雅退出
  MON->>EX: notifier.close(wait=True)  # join 线程池
  MON->>DB: db.close()                  # 长连接落盘

04 · 状态机

F = failure_threshold，R = recovery_threshold

stateDiagram-v2
  [*] --> UNKNOWN
  UNKNOWN --> UP: alive (first touch)
  UNKNOWN --> UNKNOWN: dead (fail_count++)

  UP --> UP: alive (counters reset)
  UP --> UP: dead (fail_count++)
  UP --> DOWN: dead 失败 ≥ F / 通知

  DOWN --> DOWN: alive (recover_count++)
  DOWN --> UP: alive 成功 ≥ R / 通知
  DOWN --> DOWN: dead (fail_count++)

  note right of UNKNOWN
    首次发现静默：写 events
    但不推 Webhook
  end note

防抖语义：单次失败不会触发告警，必须连续 F 次才写 events.DOWN 并调 notify_down。恢复同理。 flap（连续失败中偶发 1 次成功）会重置 recover_count。

04.5 · 日志输出（Logstash 友好）

每行 JSON，codec => json_lines 直送 ES

// 收到 SIGHUP 信号
{"ts":"2026-07-17T09:16:51+00:00","level":"INFO","logger":"fping_monitor","message":"收到 SIGHUP，强制重载配置","signal":"SIGHUP"}

// 每轮检测结果（主机数 ≤ 200：全量 results）
{"ts":"2026-07-17T09:16:51+00:00","level":"INFO","logger":"fping_monitor","message":"检测结果","event":"detection","results":{"gw":true,"dns8":false}}

// 主机数 > 200：抽样（避免单行 JSON 超 Logstash / Kafka 上限）
{"ts":"...","event":"detection","attempted":1500,"reachable":1498,"results_truncated":true,"results_sample":{"web-10.1.2.1":false,"web-10.1.2.2":false,"web-10.1.2.3":false,"sample":"down 全留 + up 抽 20"}}

// 状态机跃迁
{"ts":"2026-07-17T09:16:51+00:00","level":"INFO","logger":"fping_monitor","message":"状态变更","event":"state_change","host":"gw","ip":"192.168.1.1","tags":["network","infra"],"from_status":"UP","to_status":"DOWN","fired_kind":"DOWN"}

// 通知渠道失败
{"ts":"2026-07-17T09:16:52+00:00","level":"ERROR","logger":"fping_monitor","message":"DingTalk 业务错误","channel":"dingtalk","errcode":310000,"errmsg":"bad token"}

固定字段 ts / level / logger / message，业务字段通过 log.info(..., extra={"k":"v"}) 注入，exc_info 自动收 traceback。开发时把 config.yaml 改成 logging.format: text 看人类可读文本。

05 · 数据模型

2 张表，tags 用逗号分隔字符串存

表关键字段说明
hosts name · ip · tags · status · fail_count · recover_count · last_check · last_change 主机清单 + 当前状态机，tags 形如 prod,db,shanghai
events host_id · event (DOWN/RECOVER) · time · message 状态跃迁流水，按 host_id+time 建索引方便回溯

热加载范围：interval、阈值、fping.*、 notify.channels、logging.level、server.yaml 的 hosts 全部支持。唯独 database 路径不支持（连接在启动时建立）。 容错：YAML 解析失败时保留旧配置 + 旧 mtime，下一轮再重试， daemon 不会被错误的配置 kill。从 server.yaml 移除的主机会被 Database.delete_hosts 自动清理（连带 events 表里的历史）。

05.7 · IP 简写批量展开

一段配置自动展开成多台主机，name 加 -IP 后缀

写法含义展开数
10.1.2.3单 IP1
10.1.2.0/24CIDR（剔除 net/broadcast）254
10.1.2.0/30CIDR 短前缀2
10.1.2.3-10.1.2.10完整范围8
10.1.2.3-10短范围（end = 最后一段）8
["8.8.8.8", "1.1.1.0/30"]list 形式混合3
 
# server.yaml
hosts:
  - name: web
    ip: 10.1.2.0/28       # 自动展开为 14 台
    tags: [web, prod]

# 入库后
web-10.1.2.1   10.1.2.1   [web, prod]
web-10.1.2.2   10.1.2.2   [web, prod]
...
web-10.1.2.14  10.1.2.14  [web, prod]

安全护栏：单条 spec 最多展开 1024 个主机（防 0.0.0.0/0 这类误操作）。 展开发生在 Database.upsert_hosts，整批事务化，校验失败不会半写入。

05.8 · 健康检查（docker HEALTHCHECK）

CLI 子命令，0/1 退出码，两项检查

# Dockerfile
HEALTHCHECK --start-period=30s --interval=30s --timeout=10s --retries=3 \
    CMD ["python", "monitor.py", "healthcheck"]

# monitor.py:run_healthcheck() 的两项检查
1. Database(db_path).list_hosts()     # 验证 SQLite 可达
2. FpingDetector().detect([Host(gateway)])  # 验证 fping 工具链

# 烟测地址
healthcheck:
  gateway: 1.1.1.1            # Cloudflare DNS，改成内网 VIP 也行

设计选择：没用 HTTP server（之前是 9090 端口跑 /health + /ready + /status）—— 对 docker HEALTHCHECK 来说太重。CLI 子命令单进程、零依赖、stderr 输出失败原因，docker inspect 看得见。

05.9 · conf/ 目录约定

所有 YAML 集中放一处，docker 单目录挂载

fping-monitor/
├── conf/                   # 单目录挂载，往里加 YAML 不用改 compose
│   ├── config.yaml         # 跟踪版本：全局配置
│   ├── server.yaml         # 跟踪版本：主机列表
│   ├── server-prod.yaml    # 可选：按环境拆分（dev / staging / prod）
│   └── server.local.yaml   # 可选：本地覆盖（.gitignore 已屏蔽）
├── data/                   # bind mount，SQLite 持久化
│   └── state.db            # 状态库（hosts / events）
└── logs/                   # bind mount，日志

# docker-compose.yml
volumes:
  - ./conf:/app/conf:ro        # 整个目录挂进去
  - ./data:/app/data           # SQLite 数据
  - ./logs:/app/logs           # 日志
  # 非 root 用户运行需要把 host 目录 chown 给 10001:10001

# 切换到不同环境
docker compose run --rm monitor --servers conf/server-prod.yaml

# 本地开发覆盖
cp conf/server.yaml conf/server.local.yaml
# 改 conf/server.local.yaml（git 不会看到）

好处：新增环境、dev/prod 拆分、本地覆盖——都通过往 conf/ 里加文件完成， docker-compose.yml 和 Dockerfile 永远不用动。ConfigWatcher 也只跟踪 --config / --servers 指定的文件，加新文件不会触发误重载。

07 · 扩展点

加新通知渠道，核心三件套不动

想加什么实现什么在哪里注册
邮件告警 仿 DingTalkChannel 写 notify_down/recover _CHANNELS["email"] = EmailChannel
布谷鸟（内部） 把 CuckooChannel 占位换成真实实现 取消 config.yaml 里的注释即可
钉钉加签 已内置：填 secret 即生效，URL 自动拼 timestamp + sign config.yaml → dingtalk.secret
按 tag 路由通知 扩展 Notifier.notify_*，按 host.tags 决定走哪个 channel notifier.py
维护窗口 / 静默时段 扩展 StateMachine._advance scheduler.py
新增可热改字段 在 run_daemon 变更分支里读 watcher.cfg 并重建对应组件 monitor.py
调整防抖窗口 调 notify.min_interval_s（0=关闭）；同 (ch,host,kind) 在窗口内不重复发 config.yaml → notify.min_interval_s
同步 vs 异步派发 notify.async_dispatch: false 切回同步（测试 / 调试） config.yaml → notify.async_dispatch
Channel 配置字段校验 给新 Channel 在 notifier.py 里加一个 TypedDict，from_config 静态检查拼写错 notifier.py
schema 升级 改 sql/schema.sql 同时 bump Database._SCHEMA_VERSION，幂等 DDL 可直接追加 sql/schema.sql + database.py

不变量：新增的 Detector / Channel 只需要产出 / 接受 {name: bool} 和 Host（含 tags）这两个稳定类型。 核心三件套（Scheduler / StateMachine / Database）保持原样。Notifier 内部对 Channel 完全黑盒（同步 / 异步 / 防抖都在 Notifier 这一层决定）， Channel 本身不需要关心线程。
