架构总览

fping-monitor 的代码地图

一个 5 模块、3 协议 的轻量探活系统。核心目标是 "每周期一次 fping 批检 + 状态机带防抖 + 通知器可插拔"。本页用 4 张图带你看清：模块怎么分、数据怎么流、状态怎么变、哪里可以扩展。

01 · 模块分层

5 个职责清晰的层，从 CLI 一直到底层 fping

入口层调度层检测层通知层持久层

入口层 · monitor.py

解析 argparse，加载 YAML，调用 build_components，把控制权交给 Scheduler。

sub: run / daemon / sync / events

调度层 · scheduler.py

单次执行 run_once()；StateMachine._advance() 是纯函数式状态转移。

Scheduler · StateMachine · CycleResult

检测层 · detector.py

单次 fping 批检 + 输出解析，输出 {name: bool}。Detector 是协议，可替换。

FpingDetector · merge_results

通知层 · notifier.py

统一 notify_down/notify_recover，分发到所有 Channel，单渠道失败不影响其他。

Notifier · WeComChannel · _StubChannel

持久层 · database.py

薄封装 sqlite3，启动时应用 sql/schema.sql，对外只暴露 host/event 两类操作。

Database · upsert/list/update/event

基础设施

models.py 定义 Host/Event/HostStatus/EventType；util.py 提供 YAML、日志、fping 解析。

models.py · util.py

03 · 时序：一次 run_once 的内部调用

从 db.list_hosts() 到 webhook POST

sequenceDiagram

  participant CLI as monitor.py

  participant FP as fping

  CLI->>SCH: run_once()
  SCH->>DB: list_hosts()
  DB-->>SCH: [Host, ...]
  SCH->>DET: detect(hosts)
  DET->>FP: subprocess.run([fping, ...])
  FP-->>DET: stdout / stderr
  DET-->>SCH: {name: bool}
  SCH->>SM: step(alive)
  loop 每台 host
    SM->>SM: _advance(host, is_alive)
    SM->>DB: update_host_state(...)
    alt fired AND 旧状态非 UNKNOWN
      SM->>DB: insert_event(...)
      SM->>NT: notify_down/recover(host)
      NT->>CH: notify_down/recover(host)
      CH->>CH: requests.post(webhook)
    end
  end
  SM-->>SCH: CycleResult
  SCH-->>CLI: CycleResult

04 · 状态机

4 个跃迁路径，F = failure_threshold，R = recovery_threshold

stateDiagram-v2
  [*] --> UNKNOWN
  UNKNOWN --> UP: alive (first touch)
  UNKNOWN --> UNKNOWN: dead (fail_count++)

  UP --> UP: alive (counters reset)
  UP --> UP: dead (fail_count++)
  UP --> DOWN: dead 失败 ≥ F / 通知

  DOWN --> DOWN: alive (recover_count++)
  DOWN --> UP: alive 成功 ≥ R / 通知
  DOWN --> DOWN: dead (fail_count++)

  note right of UNKNOWN
    首次发现静默：不写入 events
    表触发通知
  end note
防抖语义：单次失败不会触发告警，必须连续 F 次才会写 events.DOWN 并调 notify_down。 恢复同理。flap（连续失败中偶尔有 1 次成功）会重置 recover_count。

05 · 源码清单

每个文件一行话

monitor.py
CLI 入口，参数解析 + 装配各组件。
scheduler.py
Scheduler.run_once + StateMachine 纯函数状态机。
detector.py
Detector 协议 + FpingDetector 实现 + merge_results。
notifier.py
Notifier 调度器 + WeCom 实现 + 钉钉/Slack/邮件占位。
database.py
SQLite 封装，schema 自动应用。
models.py
Host / Event / HostStatus / EventType 数据类与枚举。
util.py
YAML 加载、日志初始化、fping 输出解析。
config.yaml
全局配置：interval、阈值、fping 参数、通知渠道。
server.yaml
待监控主机清单。
sql/schema.sql
DDL：hosts、events 两张表 + 索引。

06 · 扩展点

加新检测器 / 新通知渠道，都不用改核心

想加什么实现什么在哪里注册
TCP 端口探活 实现 Detector.detect(hosts) -> {name: bool} 注入 Scheduler(detector=...)
HTTP 健康检查 同上，结合 merge_results 做 AND 同上
SSH 登录 同上 同上
钉钉机器人 仿 WeComChannel 写 notify_down/recover _CHANNELS["dingtalk"] = DingTalkChannel
Slack Webhook 同上 同上
邮件告警 同上（用 smtplib） 同上
二级阈值 / 维护窗口 扩展 StateMachine._advance scheduler.py
通知重试 / 死信 在 notify/ 加队列 scheduler.py + 新建 notify/queue.py

不变量：新增的 Detector / Channel 只需要返回 / 接受 {name: bool} 和 Host 这两个稳定类型。核心三件套 （Scheduler / StateMachine / Database）保持原样。
